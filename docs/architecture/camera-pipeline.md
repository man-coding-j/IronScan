# Camera pipeline

AVFoundation session mutations execute on `CameraSessionActor`. Preview analysis and capture conversion run away from `MainActor`; UI state updates run on `MainActor`. Captures are 32BGRA pixel buffers, remain in memory for local processing, and temporary captures are released after processing.

`CameraPermissionManager` checks and requests video authorization before camera startup. Denied access presents an iOS Settings action; restricted access presents device-management guidance without repeatedly requesting permission. The generated application plist uses:

```text
NSCameraUsageDescription = IronScan requires access to your camera to analyze tongue color and screen for anemia risk.
```

On physical devices, `CameraSessionActor` discovers the rear camera in this order: triple virtual camera, dual-wide virtual camera, ultra-wide camera, then wide-angle fallback. Virtual devices retain AVFoundation's automatic constituent-camera switching, allowing supported hardware to fall back to a shorter minimum-focus-distance camera when close focus requires it. Smooth autofocus is enabled when supported. AVFoundation exposes `minimumFocusDistance` as read-only device information rather than a writable distance setting, so the pipeline never fabricates a minimum-distance control.

The same actor discovers front and back devices using an explicit preference order and owns all input replacement inside `beginConfiguration()` / `commitConfiguration()`. Front-camera discovery uses wide-angle. The flip control is shown only when both positions are available. Front-camera preview is mirrored for natural self-alignment, while model and capture outputs remain unmirrored. Interface orientation is mapped once to the preview, video-data, and photo connections; on iOS 17 and later this uses `videoRotationAngle`, with a legacy `videoOrientation` adapter retained for older deployment targets. Video-data output rotation produces upright pixel buffers before local segmentation.

`CameraOpticsProfile` is switched by the three-step flow on `CameraSessionActor`. Eye capture uses centered continuous autofocus, near-range restriction when available, continuous auto-exposure, and a clamped `-0.5 EV` target bias. Nail capture stabilizes near focus, locks the closest lens position only when ultra-wide is the active macro constituent, and requests a `0.2` constant torch level when hardware supports it. Tongue capture restores standard focus range, zero exposure bias, no automatic torch, and locks the auto-selected white-balance gains rather than forcing a fabricated color temperature. Unsupported controls degrade to the closest supported AVFoundation mode.

After each successful capture, the camera returns through stabilization instead of remaining in the completed state. The actor restores the requested profile or user torch state when supported, re-locks focus and exposure where required, locks the auto-selected white-balance gains, and publishes `ready` for the next capture. The result card exposes **Scan again** only after that reset completes.

The video-data connection uses standard hardware stabilization when supported. `CameraInferenceBridge.captureOutput(_:didOutput:from:)` extracts the `CVPixelBuffer` from each sample buffer. `FrameStrideThrottle` forwards every 24th frame for live model work; overlapping live requests are dropped while the prior actor-isolated prediction is running. Two consecutive aligned observations trigger a second autofocus, exposure, and auto-white-balance stabilization cycle before capture remains ready.

Camera startup waits for valid BGRA preview delivery but does not require the engineering segmentation fixture to recognize a tongue. Manual capture becomes available after hardware stabilization and bounded luminance/clipping checks. Global luminance variance is recorded only as a coarse contrast metric; it is not labeled or used as validated sharpness. Live segmentation alignment remains optional guidance.

`MotionStabilityMonitor` owns `CMMotionManager` away from `MainActor` and computes rolling root-mean-square variation of gravity-removed user acceleration. After six samples, variation above the research threshold of `0.15 g` blocks capture and live Eye inference, cancels pending preview assessment, and presents “Hold phone steady...” over the viewfinder. Missing motion hardware does not block the simulator or supported fallback devices. This threshold is an engineering heuristic and is not a validated blur measurement.

The manual capture button depends on camera and model readiness, not advisory alignment or lighting classifications. Physical photo output prefers BGRA but accepts supported full-range or video-range bi-planar YUV and converts it directly to an in-memory sRGB BGRA pixel buffer through Core Image without JPEG or PNG encoding. Capture errors return through stabilization and report a recoverable issue instead of leaving the session permanently failed.

The multi-site view also offers optional Smart Auto-Capture while preserving the manual button. `AutoCaptureManager` serializes Vision alignment checks away from `MainActor`: face landmarks provide lower-eyelid and mouth-region guidance for Eye and Tongue, while Vision rectangle geometry provides conservative Nail framing guidance. Alignment must remain spatially steady for one second, motion variation must remain at or below the stricter `0.10 g` auto-capture threshold, and a fresh alignment signal must persist throughout a three-second countdown. Losing alignment, motion stability, or fresh frames resets the countdown with “Hold steady...” guidance. These Vision rules are framing heuristics, not validated tissue detectors, so failed automatic alignment never disables manual capture.

Camera capture requests report whether the camera actor accepted the request. A request made during actor-side restabilization is rejected immediately so the view model can restore the capture controls instead of remaining busy. Once accepted, success or failure continues to arrive through the camera event stream, preserving one owner for capture state transitions across Eye, Nail, and Tongue steps.

On the simulator, `SimulatorCameraActor` emits a bounded mock preview-event loop and procedurally generated synthetic tongue frames. The capture button routes those frames through the same local synthetic segmentation and risk-inference fixture flow. The animated preview and synthetic frame generator contain no participant images.

The centered oval overlay is alignment guidance only. Result colors correspond only to the allowed decisions `lowerObservedRisk`, `possibleRisk`, and `unableToAssess`; they are not severity categories.

Live preview frames first run `TongueSegmentation` through `SegmentationInferenceActor`. After two consecutive acceptable alignment observations and camera restabilization, `MultiInferenceEngine` evaluates the five source-dataset visual annotations at no more than one frame per second. The visual scores do not enter `RiskPrediction`. Timing is emitted through unified logging with subsystem `org.ironscan.app` and category `live-scan`; logs contain duration and errors only, never image data or participant identifiers.

The SwiftUI scan experience exposes an explicit `LiveScanningState`: idle alignment guidance, focus/lighting stabilization, three confirmed throttled visual-model evaluations, completion, or recoverable failure. `ScanningOverlayView` shows a reduced-motion-aware sweep and progress ring tied to those real evaluations rather than a decorative timer. `ScanHapticsManager` emits one alignment tick, one light pulse per evaluation stage, and a completion or warning notification. Losing alignment clears accumulated progress, and completed reports require an explicit scan-again reset before additional live inference.

`CameraInferenceBridge` is the `AVCaptureVideoDataOutputSampleBufferDelegate`. It extracts upright BGRA `CVPixelBuffer` frames on the serial sample-buffer queue, forwards bounded-rate quality frames, and forwards every configured stride to actor-isolated live segmentation. It does not invoke the risk model. Captured frames follow segmentation and color calibration before `RiskInferenceActor` accepts a `CalibratedTongueSample` and calls Core ML directly.

Raw preview frames never invoke `AnemiaRisk`: that model accepts only an accepted `CalibratedTongueSample`. The separate `IronScanMultiScreen` engineering fixture produces only source-dataset visual-annotation scores for the labeled live preview. Live disease, deficiency, and severity categories are intentionally not produced.

The simulator path validates orchestration, UI states, throttling, segmentation execution, cancellation, and temporary-buffer release. Alignment and motion thresholds are engineering heuristics. Virtual-camera switching, macro constituent selection, torch intensity, focus behavior, exposure bias, motion gating, real-tissue alignment, and physical framing still require supported-device validation.
